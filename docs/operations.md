## Конфигурация

Все настройки берутся из окружения; шаблон [`.env.example`](../.env.example).
Compose читает `.env` автоматически. Новая установка использует имя проекта
`finance-tracker-clean`; режим разработки использует `finance-tracker-clean-dev`.
Секреты и данные действующего стека
сохраняются при обновлении. Для нового публичного стенда задайте собственные
пять паролей PostgreSQL, `REDIS_PASSWORD` и `JWT_SECRET`, файл `.env` храните с правами 600.

| Переменная | Сервис | По умолчанию | Назначение |
|---|---|---|---|
| `JWT_SECRET` | gateway, auth | Обязательна | секрет подписи токенов, не короче 32 байт: `openssl rand -base64 32` |
| `AUTH_REGISTRATION_EMAILS` | auth | Пусто, регистрация закрыта | email через запятую, максимум 100; без подтверждения владения адресом |
| `REDIS_PASSWORD` | redis, ledger | Обязательна для Compose | независимый случайный пароль от 32 байт, пользователь ACL `ledger` |
| `JWT_TTL` | auth | `24h` | срок жизни токена, не больше `720h` |
| `LOG_LEVEL` | все | `info` | `debug`, `info`, `warn`, `error` |
| `LOG_FORMAT` | все | `json` | `json` или `text` |
| `TZ` | все | `Europe/Moscow` | часовой пояс; в ledger определяет дату «сегодня» для транзакций без даты |
| `SHUTDOWN_TIMEOUT` | все | `10s` | сколько ждать завершения запросов при остановке |
| `HTTP_PORT` | gateway | `127.0.0.1:8080` | адрес и порт публикации Gateway в основном Compose |
| `FINANCE_DOMAIN` | caddy | нет, обязательна для HTTPS | публичное имя API без схемы и пути, например `api.example.com` |
| `HTTPS_GATEWAY_PORT` | gateway | `8080` | порт на `127.0.0.1` в `compose.https.yaml`; заменяет публикацию из `HTTP_PORT` |
| `HTTP_ADDR` | gateway | `:8080` | адрес, который слушает gateway |
| `LEDGER_GRPC_ADDR`, `AUTH_GRPC_ADDR` | gateway | `localhost:9090`, `localhost:9091` | адреса сервисов; в compose: `ledger:9090`, `auth:9091` |
| `LEDGER_TIMEOUT`, `AUTH_TIMEOUT` | gateway | `10s` | сколько ждать ответа сервиса, потом `504`; таймаут записи HTTP-ответа: на 20 с больше большего из них |
| `IMPORT_TIMEOUT` | gateway | `1m` | срок каждой из двух фаз CSV-импорта по отдельности: чтения тела запроса и вызова Ledger; между ними разбор файла, после каждой запас 20 с на запись ответа, так что весь запрос может длиться дольше одного `IMPORT_TIMEOUT` (см. [сроки импорта](api.md#csv-импорт)) |
| `GRPC_ADDR` | ledger, auth | `localhost:9090`, `localhost:9091` | адрес gRPC-сервера; по умолчанию только loopback, в compose: `:9090`/`:9091` внутри сети контейнеров |
| `LEDGER_GRPC_PORT`, `AUTH_GRPC_PORT` | ledger, auth | `9090`, `9091` | порты на `127.0.0.1` хоста, только с `compose.dev.yaml` |
| `DATABASE_URL` | ledger, auth | Пусто | строка подключения к PostgreSQL; пустое значение включает хранилище в памяти. Учётные данные можно передать через `PGUSER` и `PGPASSWORD`, как в Compose |
| `DB_CONNECT_WAIT` | ledger, auth | `30s` | сколько ждать базу при старте (она может подниматься дольше сервиса) |
| `REDIS_URL` | ledger | Пусто | Redis для кеша отчётов, `redis://host:6379/0`; пустое значение отключает кеш. В Compose: `redis://redis:6379/0` |
| `REPORT_CACHE_TTL` | ledger | `5m` | сколько живёт отчёт в кеше |
| `IMPORT_WORKERS` | ledger | `4` | сколько строк импорта записываются одновременно: на все импорты вместе; не больше половины `DB_MAX_CONNS` |
| `DB_MAX_CONNS` | ledger | `16` | размер пула соединений с PostgreSQL |
| `REDIS_PORT` | redis | `6379` | порт Redis на `127.0.0.1` хоста, только с `compose.dev.yaml` |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | db | `finance` | учётные данные сервиса `db` |
| `POSTGRES_PORT` | db | `5432` | порт базы на `127.0.0.1` хоста, только с `compose.dev.yaml` |

Таблица описывает переменные программ и Compose. Контейнеры получают только
параметры из `environment` соответствующего сервиса: например, переопределение
`SHUTDOWN_TIMEOUT` требует добавить его туда через собственный Compose override.

## Локальная разработка

Команды выполняются из корня репозитория. Нужен Go 1.26.9 или новее;
`go.mod` задаёт минимум, стандартный `GOTOOLCHAIN=auto` выбирает подходящий toolchain.
Для полного Docker-стека используйте [быстрый старт](../README.md#быстрый-старт).

```sh
make db
make migrate
make run
```

В `compose.dev.yaml` Redis работает без ACL для `FLUSHDB` в тестовой DB 15.
Этот режим публикует порт только на loopback и предназначен для отдельного стенда.
`make run` не передаёт ему производственный `REDIS_PASSWORD`.

`make db` запускает PostgreSQL и Redis в отдельном Compose-проекте
`finance-tracker-clean-dev`. Для `make run` задайте в `.env` `DATABASE_URL` с адресом
этой базы, `JWT_SECRET`, пять независимых паролей из `.env.example` и при необходимости `REDIS_URL`.
`make migrate` использует роли `auth_migrator` и `ledger_migrator`;
`make run` передаёт сервисам только пароли `auth_app` и `ledger_app`. Примеры локальных
адресов есть в `.env.example`; порты определяются `POSTGRES_PORT` и `REDIS_PORT`.

`make run` собирает бинарники, запускает Auth и Ledger, ждёт их gRPC health,
затем запускает Gateway. При ошибке старта команда завершается; Ctrl+C останавливает
сервисы. Без `DATABASE_URL` используются хранилища в памяти, Redis отключён.
`make down-dev` останавливает отдельные PostgreSQL и Redis, сохраняя тома.
Старые данные между Compose-проектами автоматически не переносятся.

## Прямой доступ к gRPC

Для разработки можно поднять весь отдельный стек с loopback-портами:

```sh
HTTP_PORT=127.0.0.1:18080 docker compose -p finance-tracker-clean-dev \
  -f compose.yaml -f compose.dev.yaml up -d --build --wait
```

Не запускайте одновременно `make run` и контейнеры тех же сервисов на одинаковых
портах. Этот override не используется на VPS.
Выполните [полный пример API](api.md#примеры) с
`BASE_URL=http://localhost:18080`, чтобы получить `DEMO_USER_ID` именно этой базы.
Сервисы поддерживают reflection:

```sh
grpcurl -plaintext localhost:9091 list
grpcurl -plaintext localhost:9090 list
grpcurl -plaintext -d "{\"user_id\":$DEMO_USER_ID}" \
  localhost:9090 ledger.v1.LedgerService/ListBudgets
grpcurl -plaintext -d '{"service":"ledger.v1.LedgerService"}' \
  localhost:9090 grpc.health.v1.Health/Check
```

## Публичный HTTPS

Caddy принимает HTTPS и обращается к `gateway:8080` через `edge`.
PostgreSQL, Auth и Ledger используют `core`. Redis доступен Ledger в отдельной
внутренней сети `cache`, с ACL и отдельным паролем. Для новой установки:

1. Установите Docker Engine с Compose 2.24.4 или новее
   ([инструкция для Ubuntu](https://docs.docker.com/engine/install/ubuntu/)).
   Скопируйте репозиторий на сервер и подготовьте `.env` со случайными секретами.
2. Задайте `FINANCE_DOMAIN` как имя без схемы и пути, например `api.example.com`,
   и `HTTPS_GATEWAY_PORT=8080`. Это loopback-порт Gateway для серверной диагностики.
3. Направьте A-запись домена на публичный IPv4 сервера. AAAA добавляйте только
   при настроенном IPv6. Разрешите TCP 80/443 у провайдера и на сервере,
   сохранив SSH. Проверьте также правила Docker: публикации могут обходить UFW.
4. Из каталога репозитория проверьте конфигурацию, соберите и запустите сервисы:

   ```sh
   docker compose -f compose.yaml -f compose.https.yaml config --quiet
   docker compose -f compose.yaml -f compose.https.yaml build
   docker compose -f compose.yaml -f compose.https.yaml run --rm --no-deps \
     caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
   docker compose -f compose.yaml -f compose.https.yaml \
     up -d --no-build --wait --wait-timeout 300
   ```

5. С внешнего клиента проверьте сертификат, перенаправление HTTP на HTTPS,
   `/ping`, `/docs`, 401 без JWT, затем вход и [сценарий API](api.md#примеры).
   Healthcheck Caddy подтверждает доверенный TLS и `/ping`, но не работу Auth и Ledger.
6. Подключите [Google Таблицу](sheets.md), выполните [демонстрацию](demo.md).

Caddy хранит сертификаты и ключи в `caddy_data`, состояние в `caddy_config`.
При обновлении сохраняйте оба тома и `pgdata`. Административный API Caddy
отключён; наружу публикуются только TCP 80/443.
Не объединяйте HTTPS-конфигурацию с `compose.dev.yaml`.

Caddy собирается из стандартной точки входа закреплённой версии, отдельный
Go-модуль находится в [deploy/caddy](../deploy/caddy). Его `main.go` скопирован
из Caddy v2.11.7 с сохранением уведомления об авторских правах;
[Apache License 2.0](../deploy/caddy/LICENSE) относится к этому исходному файлу.
PostgreSQL и Redis также
используют [производные Dockerfile](../deploy) с исправленными библиотеками ОС.
Базовые digest и версии заданы в Dockerfile и модулях;
[результаты сканирования](security.md#находки-образов-и-применимость) относятся
к конкретному проверенному выпуску.

## Роли PostgreSQL и переход существующей базы

Новые базы настраивает [roles.sh](../deploy/postgres/roles.sh) при инициализации.
Пароль администратора `POSTGRES_PASSWORD` получает только контейнер БД.
Имена ролей фиксированы, пароли задаются отдельно:

| Роль | Переменная пароля | Права |
| --- | --- | --- |
| `auth_app` | `AUTH_DB_PASSWORD` | SELECT/INSERT `auth.users`, USAGE её последовательности |
| `ledger_app` | `LEDGER_DB_PASSWORD` | SELECT/INSERT `ledger.transactions`, SELECT/INSERT/UPDATE `ledger.budgets`, USAGE последовательности расходов |
| `auth_migrator` | `AUTH_MIGRATION_PASSWORD` | Владелец схемы `auth` и её объектов |
| `ledger_migrator` | `LEDGER_MIGRATION_PASSWORD` | Владелец схемы `ledger` и её объектов |

У ролей нет superuser, CREATEDB, CREATEROLE, REPLICATION, BYPASSRLS,
доступа к чужой схеме и временным таблицам. Рабочие роли не могут менять
схему, удалять строки и обращаться к таблицам версий Goose.
Пароли миграций получает отдельный бинарник `cmd/migrate`, который завершает
работу после миграций и выдачи точных прав. Они не передаются Auth или Ledger.
После выпуска можно удалить завершившиеся контейнеры миграций командой
`docker compose rm -f auth-migrate ledger-migrate` с параметрами своего проекта.
Доступ к Docker и `.env` остаётся административным доступом ко всему стеку.

При обновлении существующего тома initdb-скрипты автоматически не повторяются.
Остановите запись и сохраните проверенную резервную копию по разделу
[обновления](#обновление-и-откат). Добавьте четыре новых пароля в существующий
`.env`, сохранив прежний `POSTGRES_PASSWORD`. После загрузки новых образов
запустите только `db` и `redis`, затем выполните из каталога выпуска:

```sh
docker compose up -d --no-deps --wait db redis
docker compose exec -T db /docker-entrypoint-initdb.d/10-roles.sh
docker compose run --rm --no-deps auth-migrate
docker compose run --rm --no-deps ledger-migrate
docker compose up -d --wait
```

Во всех командах используйте те же `-p`, `--env-file` и `-f`, что у установки.
Для комплекта готовых образов добавьте `--no-build --pull never` к `up`.
Скрипт в одной транзакции переносит прежние пять таблиц из `public` в `auth`
и `ledger`, включая индексы и принадлежащие таблицам последовательности,
меняет владельцев и сохраняет записи Goose. Повторный запуск безопасен для
данных; пароли ролей приводятся к значениям из окружения контейнера БД.
Существующие схемы `auth` и `ledger` должны принадлежать соответственно
`auth_migrator` и `ledger_migrator`. При другом владельце скрипт отказывается
от изменений в той же транзакции; сначала нужен разбор владельцев и данных.
Роли с членством в других ролях и конфликт имён таблиц требуют ручного разбора,
скрипт останавливается. Новые миграции должны сопровождаться явным обновлением
прав в `cmd/migrate`, автоматических прав на будущие таблицы нет.

Прежние образы ищут таблицы в `public`. Для возврата к ним восстановите
согласованную копию базы и старую конфигурацию до возобновления записи.
Одной замены образов после переноса схем недостаточно.

## Установка готового комплекта

На сервере с небольшим объёмом памяти используйте заранее собранные образы
нужной архитектуры. Подготовленный комплект linux/amd64 содержит `images.tar.gz`,
`release-manifest.json`, `SHA256SUMS`, `verify-release.py`, три Compose-файла,
Caddyfile, файлы Google-клиента и `INSTALL.txt`. Это отдельный артефакт выпуска;
скрипты его проверки не входят в обычный checkout репозитория.
Секреты, дампы и сертификаты в комплект не включаются. Новый комплект должен
содержать также образ `finance-release-migrate` с тем же тегом; прежние
комплекты из шести образов не подходят к новой конфигурации ролей.

После передачи комплекта по SSH, из его каталога:

```sh
sha256sum -c SHA256SUMS
python3 verify-release.py --files-only
docker load --platform linux/amd64 --input images.tar.gz
python3 verify-release.py
```

В окружении задайте `FINANCE_RELEASE_TAG` из манифеста,
`FINANCE_PGDATA_VOLUME` как фактическое имя существующего тома PostgreSQL
и `FINANCE_DOMAIN`. Выберите существующие `.env` и имя Compose-проекта.
Пример для проекта `finance-tracker`:

```sh
docker compose -p finance-tracker --env-file /opt/finance-tracker/.env \
  -f compose.yaml -f compose.https.yaml -f compose.images.yaml config --quiet
docker compose -p finance-tracker --env-file /opt/finance-tracker/.env \
  -f compose.yaml -f compose.https.yaml -f compose.images.yaml \
  up -d --no-build --pull never --wait --wait-timeout 300
```

[compose.images.yaml](../compose.images.yaml) убирает сборку и скачивание,
выбирает теги готового выпуска и подключает PostgreSQL как внешний том.
Ошибочное имя тома останавливает запуск. Для новой установки том создаётся
отдельно; при обновлении должен использоваться прежний.

## Обновление и откат

1. Выберите выпуск с успешными проверками исходников и готовых образов.
   Сохраните предыдущие образы, Compose-файлы, Caddyfile, `.env`, команду запуска
   и фактические имена томов. Локальный прогон не является запуском GitHub Actions.
2. Сделайте предварительный дамп PostgreSQL в custom-формате, сохраните роли,
   схему и оба тома Caddy. Архив конфигурации и дампы могут содержать секреты;
   храните их отдельно от Git с доступом только владельцу.
3. Восстановите дамп в отдельной базе совместимой версии PostgreSQL. Проверьте
   таблицы, данные, версии миграций, владельцев и последовательности, включая
   `is_called`. Простое чтение списка объектов дампа не подтверждает восстановление.
4. Проверьте совместимость миграций со старой версией приложения и порядок возврата.
   Если прежние образы не работают с новой схемой, откат требует восстановления
   базы. Такой возврат теряет записи, сделанные после резервной копии.
5. Перед переключением остановите приём записей: Caddy, Gateway, Ledger и Auth.
   Снимите финальный согласованный дамп и проверьте восстановление. Сохраните
   сертификаты и конфигурацию, зафиксируйте контрольные суммы резервной копии.
6. Установите образы, запустите PostgreSQL и Redis. Выполните
   [переход на отдельные роли](#роли-postgresql-и-переход-существующей-базы),
   затем запустите сервисы приложения и Caddy.
   Сохраните прежние пароль базы, JWT-секрет, Compose-проект и тома.
7. Проверьте health, вход, бюджеты, прежние расходы, CSV, отчёт, HTTPS и Google-клиент.
   При неуспехе остановите запись, верните согласованную конфигурацию и образы;
   базу восстанавливайте только по проверенному плану совместимости.

Перед обновлением подготовьте независимый `REDIS_PASSWORD` и список допуска
`AUTH_REGISTRATION_EMAILS`. Отсутствие списка закроет только регистрацию,
существующие аккаунты продолжат входить.

Миграция категорий версии 2 использует тот же Go-нормализатор, что и API.
Она зарегистрирована в `cmd/migrate`: используйте `make migrate` или
штатные контейнеры миграторов. Запуск только SQL-файлов через отдельный Goose CLI
не выполняет этот шаг.

Под блокировкой обеих таблиц сначала проверяются все категории, затем меняются
имена. При коллизии, недопустимой последовательности комбинируемых знаков или
результате длиннее 64 символов миграция отказывается до изменения данных.
Goose сохраняет строки и прежнюю версию; после исправления данных миграцию
можно повторить. Ошибка не содержит категорию и ID пользователя.
На копии базы вручную согласуйте расходы и бюджеты конфликтующих категорий
либо переименуйте неподдерживаемые имена. Автоматического выбора лимита,
объединения и обрезания имён нет. Обратная миграция не восстанавливает прежнее
написание, для этого нужен дамп.

Версия 2 уточнена до выпуска на VPS. Если прежняя SQL-версия 2 уже применялась
на отдельном локальном стенде, Goose не выполнит её повторно. Проверяйте переход
на восстановленной копии базы до версии 2; не удаляйте запись версии в рабочей
базе. Настоящий VPS в этой локальной проверке не менялся.

При обновлении Apps Script сначала проверьте четыре файла в приватной копии,
затем перенесите их в основную таблицу и повторите сценарий. Смена адреса API
требует повторного входа. Сохраните предыдущий скрипт и адрес до переключения.

## Повторный запуск установленного выпуска

Для установки в `/opt/finance-releases` используйте сохранённую команду запуска:
она выбирает выпуск, `.env`, Compose-проект и внешний том PostgreSQL.
Перед остановкой сохраните свежую резервную копию по порядку выше.
Остановка всех сервисов прерывает доступ к API.

```sh
/opt/finance-releases/finance-compose.sh config --quiet
/opt/finance-releases/finance-compose.sh stop --timeout 30 caddy gateway ledger auth redis db
/opt/finance-releases/finance-compose.sh up -d --no-build --pull never --wait --wait-timeout 300
/opt/finance-releases/finance-compose.sh ps
```

Проверьте шесть healthy-сервисов, сохранённые данные, прежний сертификат,
внешний API и отчёт Google. Redis не сохраняет кеш на диск: первый отчёт
после его перезапуска даёт MISS, следующий запрос в течение TTL даёт HIT.
Не используйте `down -v` для рабочего стека.


## Закрытый пилот и квоты

До открытия внешнего доступа внесите email участников в `AUTH_REGISTRATION_EMAILS`
и пересоздайте Auth. Список ограничивает адреса, но не подтверждает их владельцев:
человек, знающий разрешённый email, может занять его первым. Создавайте аккаунты
в контролируемом сеансе через локальный доступ, затем очистите список и
пересоздайте Auth. Участникам передавайте доступ по отдельному доверенному каналу.
Удаление email из списка не отключает готовый аккаунт и его JWT.

Одна установка допускает 100 аккаунтов, каждый до 10 000 транзакций и
100 категорий в объединении расходов и бюджетов. Квоты проверяются в транзакции
БД под блокировкой; повторная запись с тем же ключом не расходует квоту.
Перед переносом старой базы проверьте её объём: избыточные данные автоматически
не удаляются. Квоты ограничивают логические записи, но не заменяют контроль
свободного диска, WAL, журналов и резервных копий. При достижении квоты пользователь
может читать и экспортировать данные; увеличение лимита требует отдельного решения.

Redis запускается от пользователя `redis` с read-only корневой файловой системой.
ACL содержит хеш пароля во временном файле с правами 600; исходный пароль убирается
из окружения процесса Redis. Docker всё ещё хранит окружение контейнера, поэтому
доступ к Docker равнозначен доступу к секретам. Разрешены только команды кеша
и ключи `report:v2:*`; `CONFIG`, `FLUSHDB` и чужие пространства ключей запрещены.
Gateway, Auth и миграторы не получают пароль Redis.

## Регулярное резервирование

До приёма чужих финансовых данных нужен работающий внешний резервный контур.
Для пилота исходный ориентир: потеря не более 24 часов записей, восстановление
за 4 часа. Эти сроки требуют проверки на фактическом объёме базы.

1. Ежедневно сохранять согласованный custom-дамп PostgreSQL, необходимые роли
   и конфигурацию; перед обновлением дополнительно сохранять образы и тома Caddy.
2. Шифровать копии и передавать на отдельное хранилище вне VPS. Ключ расшифрования
   хранить отдельно. Ограничить доступ, не включать копии и секреты в Git.
3. Хранить 7 ежедневных и 4 еженедельные версии. Проверять завершение копирования,
   контрольную сумму и возраст последней успешной копии. Возраст более 26 часов
   или ошибка копирования требуют уведомления ответственного.
4. Ежемесячно восстанавливать копию в отдельной БД, проверять вход, бюджеты,
   суммы, последовательности и роли. Записывать длительность и результат,
   после проверки удалять только принадлежащий ей стенд.
5. Назначить ответственного за уведомления и восстановление. Само наличие
   дампа или расписания без внешней копии и пробного восстановления недостаточно.

Это требования к эксплуатации. Их установка и проверка на VPS выполняются
отдельно от локальных исправлений приложения.
